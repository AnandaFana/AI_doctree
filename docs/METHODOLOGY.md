# 从目录整理到可维护的项目树

> 本文保留 v1 的教学方法与决策过程，不代表当前默认技术路线。当前版本采用“Markdown 共享依据 + 轻量管理目录 + 人类树图”，规范与接入步骤见 [Markdown 节点协议 v2](MARKDOWN_PROTOCOL_V2.md)。下文“本轮”“当前”“后续”均指 v1 探索；其中有用的职责、来源与验证原则仍可复用。

v1 选择“逻辑树 + 旁路映射 + 局部证据版本”的路线：文件保留在原位，逻辑树表达职责与工作关系。两个教学样例用于验证叶节点交付、祖先失效和逐级汇总。v2 将目录职责与父子导航写入用户选择的 Markdown，让共享知识随项目流转；旁路映射与历史状态作为可选详细功能保留。

本文记录方法与决策依据。实际执行次数、耗时、冲突测试结果、浏览器验收和副本前后指纹由本次运行的验证记录负责；本文不把设计预期写成测试已经通过。

## 1. 用什么决定一个节点

节点的对象是“有独立职责、状态和证据入口的工作单元”，不等同于每个物理文件夹。先问三个问题：这里负责回答哪个问题，什么变化值得上级知道，谁能凭哪些依据决定下一步。三者都没有独立答案时，通常应作为某节点的成员文件或证据。

首轮可用下表帮助讨论粒度。这是人工整理辅助量表，不是经验证的自动分类器或强制行业规则。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 职责独立性 | 与父节点完全重复 | 有子用途但难独立描述 | 有明确独立问题或交付 |
| 状态独立性 | 状态始终与父一致 | 偶有独立待办 | 有独立阻塞、验收或决策 |
| 证据完整性 | 只是零散输出 | 有可定位成员 | 有入口、原始依据和来源边界 |
| 下钻价值 | 展开仍是重复正文 | 有几份相关文件 | 能帮助定位负责人或下一步 |

总分 6–8 可优先建节点，3–5 先作逻辑分组候选，0–2 常适合作为证据或附件。阈值是这次试验的启发式起点；小型目录无需打分，跨团队目录需要加入归属与权限维度。重要的失败记录可以作为证据保留，不必为每个失败输出建一棵树。

对于包含批次结果、归档和打包镜像的项目，默认导航应避免被重复产物占满。是否为这些目录建立说明由项目维护者决定；可以先治理职责明确的少数目录，再按深度扩大范围。目录数量、README 覆盖与阅读收益应分开衡量，不能仅以节点数量判断整理是否有效。

## 2. v1 为什么试验旁路映射

| 方案 | 维护成本与收益 | 本轮判断 |
|---|---|---|
| 每个物理目录补 README | 位置直观；缓存、批次、镜像会制造大量重复节点 | 不作为默认方案 |
| 先搬动文件，再按新目录治理 | 目录和树容易一致；旧链接、脚本、冻结哈希与复现入口可能失效 | 第一轮不采用 |
| 全仓语义向量或模型自动聚类 | 可帮助搜索；分类难解释，当前状态与旧记录容易混合 | 留作可选发现助手 |
| 工具侧稳定 ID 与语义映射 | 原始文件保留；规则可审阅，可逐步迁移协议 | 本轮采用 |
| 成熟节点自带 README 协议 | 责任和上下文可跟随项目；需协调所有者和迁移流程 | 样例验证，后续按节点逐步采用 |

映射本身是可审阅的产物：[projects.json](../config/projects.json)。它具有版本控制和明确来源路径；不把候选摘要伪装成原项目负责人认可的状态。扫描只是读取已选择文本及指纹，不 import 被扫描项目模块，不执行 Markdown 中出现的命令。

## 3. 一次可复用的接入流程

1. **固定授权与边界。** 记录实际路径、是否副本、Git 元数据或重解析点情况、原仓库是否实际访问。副本无远端并不单独证明内容独立，还应检查符号链接、junction、硬链接或 Git worktree 指针。当前工具只把必要的安全事实写入报告，不扫描整台机器。
2. **建立接入前基线。** 保存范围明确的文件清单、SHA-256、数量与字节总量，另记录 Git HEAD 和工作区状态（若存在）。没有 Git 时内容指纹仍是有效基线；仅有 HEAD 不能代表未提交工作区。
3. **识别现行入口。** 从根 README、现行计划、总账、来源清单和明确的替代说明开始。文件较新、标题带 FINAL 或检查框未勾选都不是充分的当前状态依据。
4. **列出职责与证据角色。** 区分正文工作源、科学协议、实际采样、派生分析、解释报告、历史记录、生成产物和打包镜像。各角色分别保留，不用一个“完成”覆盖。
5. **形成候选语义树。** 每节点使用稳定 ID、单父关系、用途、一句话候选摘要、证据引用和结构化限制。跨节点依赖用 related，不复制节点。
6. **校验可追溯性。** 检查引用是否存在、父节点是否唯一、是否有环、是否跨出允许根路径；明确被排除的范围和缺失文件。映射中的文件不能被模糊 glob 静默替换成另一个版本。
7. **选择小型真实交接任务。** 导出某节点上下文；Codex 真实阅读必要文档，处理一个可核对问题，保留来源范围，生成交付候选。教学记录只能作为输入夹具，不能假装是真实计算证据。
8. **验证失效与汇总。** 单叶变化只使其祖先待汇总；连续两叶变化都必须进入父摘要依据。过期汇总拒绝覆盖，重复导入幂等，中断后仍能恢复队列。自然语言审阅和确定性字段传播分别留痕。
9. **对比基线与结论。** 接入后对比范围相同的指纹。若来源变化，报告哪些路径变化及是否与工具写入清单一致；无法归因时写“检测到变化，来源待核查”，不能猜测工具或外部进程责任。
10. **再决定成熟节点迁移。** 稳定使用后才将批准的协议写入业务 README；预览补丁、逐节点应用、保留旧入口或重定向。此阶段不要求移动原始证据，也不删除历史。

其他文件夹接入时可以复制配置结构，替换 ID、路径和语义映射，并重复同一检查。项目特有的流程编号、阶段枚举解释或来源优先级应留在项目说明或可选扩展中。

交接版本还须区分“开始任务时读到的版本”和“完成自己改动后准备导入的版本”。Agent 修改叶证据后，应刷新，检查实际差异恰是自己的预期改动，再用当前版本作为导入 based_on_version；最初上下文版本保留在验证记录中。发现其他修改时重新核对，不盲目把交付版本改成最新来绕过冲突保护。

## 4. 当前信息、历史与证据的优先级

优先级先按适用范围和来源职责解释，再看时间：

- **当前范围决定**回答现在做什么；必须有明确适用范围或替代声明。
- **冻结协议与原始结果**回答当时按什么规则得到什么；后续范围缩小不改写其失败或未完成标志。
- **现行正文与聚合说明**回答如何表述证据；聚合解释不替代原始数据或冻结规则。
- **旧报告、交接和归档**回答当时如何认识与行动；旧“下一步”保留，不自动变成当前待办。
- **生成输出与上传镜像**回答某个版本如何交付；文件齐备不等同于作者认可或科学验收。

例如，教学记录中的原计划要求覆盖所有场景，而后续明确决定只交付已验证的一部分。当前范围缩小可以支持有限交付，同时保留原更广目标未完成；二者无需相互覆盖。重新生成的恢复文件也应记录新的来源和哈希，不能冒充旧文件的原始字节或第二次独立验证。

当两份现行权威来源确实冲突，没有明确替代关系时，加入待决策标记并展示两份依据。不要用“最新文件赢”或生成摘要把冲突抹平。

## 5. 状态是四个问题

| 状态轴 | 它回答的问题 | 不能顺推的结论 |
|---|---|---|
| delivery | 要交出的文件或改动是否形成 | 已并入目标代码 |
| integration | 目标版本是否包含改动 | 目标环境已经成功运行 |
| execution | 某次规定的运行或操作是否完成 | 结果满足业务或科学目标 |
| acceptance | 特定范围的结论是否有明确验收 | 所有模型、环境或未来版本都通过 |

候选摘要的 `review` 表示文档治理审阅状态。Agent 核对一句话与来源一致，可以将该摘要标记为 reviewed，但不会因此把 scientific acceptance 改成 complete。新映射默认保持 candidate；来源文档自述的 PASS 在摘要中使用“来源报告”措辞。

阻塞、待验证和待决策分别是结构化集合。它们要随汇总确定性向祖先传播，去重并保留来源节点，不能只寄希望于自然语言记住限制。父节点四个阶段应有自己的依据，不简单用“所有孩子完成”自动赋值。

## 6. 本轮实验设计

教学项目 A 有“项目 → 策略研究 → 策略 → 实验 A/B”路径，数据说明是独立兄弟节点。实验 A 的草稿故意把执行成功写成研究通过；实验 B 的草稿故意忽略新范围决定。实际任务是 Codex 阅读这些固定来源并修正文档，能验证文档治理闭环，又不制造新的科研结果。

教学项目 B 展示交付包完成但未集成、集成与执行完成但业务验收待定的不同状态组合。所有示例执行状态都明确标为教学输入；本工具实际测试结果必须另行记录。

| 检查 | 操作 | 应观测到的性质 |
|---|---|---|
| 语义导航 | 打开研究样例并沿路径下钻 | 看到策略、实验和原始依据 |
| 局部失效 | 修改实验 A 证据并刷新 | A 的祖先待汇总，数据兄弟与软件项目保持原状态 |
| 合并两叶 | A、B 先后变化，期间保留未处理状态 | 父节点依据包含两个新版本 |
| 过期覆盖 | 在汇总候选生成后再改变子证据 | 导入拒绝旧输入，重新排队 |
| 中断恢复 | 待汇总时退出，再启动或扫描 | 变化与队列仍在 |
| 幂等 | 重复导入同一交付或重复处理相同输入 | 不制造重复业务事件或丢失状态 |
| 来源只读 | 比较副本前后基线 | 工具写入清单与来源变化可区分 |
| 安全显示 | Markdown 包含脚本式文本 | 仅作文本展示，不执行 |

这张表是验收设计。应以测试输出、事件记录与浏览器证据填写实际结果，不以本表替代验证。

## 7. 演进方向和升级门槛

第一版优先把一个协调者的版本核对、持久化和上下文包做正确。规模扩大后可在协议不变的前提下增加增量扫描、按职责搜索、外部节点引用、权限与审阅身份、来源解析插件和局部 README 迁移补丁。

自然语言模型可以辅助发现和提出摘要，但不得直接绕过输入版本检查。若加入向量检索，应返回源节点、版本和原始证据；若引入实时监听，应继续排除生成区与临时文件；若支持并发写入，应先验证锁、冲突与恢复行为。跨项目 related 的语义、访问权限以及是否触发依赖提醒要单独定义，不能默认等同于主树祖先失效。

协议变更由 schema 明确表达。可选字段增加需要旧读取器安全忽略；身份、父关系、证据含义或哈希算法变化需要显式迁移与新的扫描算法版本，不静默重用旧指纹。
